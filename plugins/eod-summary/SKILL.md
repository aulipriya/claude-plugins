Reconstructs what the user accomplished — including exploration and decisions that left no commit — by distilling each session transcript and summarizing it with one subagent per session. Use when the user invokes `/eod-summary [--date YYYY-MM-DD] [--path DIR] [--dry-run] [--no-sessions] [--max-sessions N] [--browser] [--browser-profile NAME] [--open-tabs] [--drive-folder NAME]`, or says they are done for the day ("I'm finished for today", "wrap up my day", "that's it for today", "write up what I did today").

# eod-summary

## Invocation

```
/eod-summary [--date YYYY-MM-DD] [--path DIR] [--dry-run] [--no-sessions] [--max-sessions N]
             [--browser] [--browser-profile NAME] [--open-tabs]
             [--drive-folder NAME]
```

- `--date` (default: today) — rebuild any past day; every data source is on-disk or server-side history.
- `--path` (default: `~/Documents`) — root to scan for repos, and the filter for which sessions count.
- `--dry-run` — print the summary in chat, skip the Google Doc.
- `--no-sessions` — git layer only. Fast and cheap; loses the exploration/decision layer.
- `--max-sessions` (default: 10) — cap on sessions summarized.
- `--browser` — opt in to the Chrome history layer (off by default). `--browser-profile NAME`
  restricts it to one Chrome profile (name, directory, or account e-mail) — use it when one
  profile is personal. `--open-tabs` additionally reads the tabs open right now (needs macOS
  Automation permission). Either of those two implies `--browser`.
- `--drive-folder NAME` — opt in to the Drive layer: the named folder's tree is checked for
  files updated that day. No default; without it the layer is skipped.

**Conversational trigger:** if the user says they've finished for the day, run this. If it's
ambiguous (they merely mention being tired, or are mid-task), ask first — a full run costs
real tokens and publishes to Drive.

## The rules

> The report is **the user's own end-of-day notes, for self-review** — what got done and
> what's worth being pleased about. It is not a status report for anyone else, not what
> Claude did, and not how the report itself was made.

**Lead with the wins.** The day's 2–4 biggest achievements go in a `## Wins` section right
under the title — the things worth remembering about today (something shipped, a mystery
solved, a plan settled). Each says what it was and, briefly, why it matters. Don't repeat a
win in its project section.

**Voice — casual notebook.** Write like a developer jotting notes for themselves: plain words,
short fragments, subject usually dropped ("Got PR #25 merged", "Finally found why …"). A little
personality is fine where it's earned — "finally", "big one", "oops" — but no hype, no
exclamation-mark cheerleading. No "you", no "Claude", no "the assistant", no formal
report-speak ("was completed", "has been addressed", "deliverables").

- ✅ "Got PROJ-142 merged to main (PR #31) — all tests green."
- ✅ "Retry logic only fires on the first timeout, not every one. Oops."
- ❌ "The PROJ-142 refactor was committed, pushed and merged to main through PR #31."
- ❌ "You fixed the parser at the root — normalizing the input before validation, …"
- ❌ "Claude ran a script that counted the videos and reported back."

**No mechanics, no run statistics.** Strip tool names, agent counts, thread/session/transcript
counts, token and file-size figures, compression ratios, retries, and any description of how
the work was carried out. A fan-out of eight agents was *one activity*, not eight. The doc has
**no "generated by" footer** and no source statistics — those belong only in the chat report
(step 8).

- ❌ "Two threads today. …" / "3 sessions — 11 transcripts, 347 MB, distilled to 314 KB."

**Brevity.** Target 200–350 words for a normal day; never more than 500. One-line "day in a
sentence" under the title. Wins: 2–4 bullets. Each project: 2–5 bullets of one line each. "For
tomorrow": at most 6 bullets in total.
Keep a number only when it *is* the deliverable (endpoints shipped, bugs closed, records
migrated); drop process metrics (files read, log lines scanned, GB transferred, minutes
spent). Cut narrative connective tissue ("more importantly", "and chasing that turned up",
"worth keeping"). Keep findings, decisions, outcomes, and what was left unfinished.

- ✅ "Fixed the weekly export: a case mismatch had silently dropped one region (11 → 12 regions)."
- ❌ "You audited the weekly export across all twelve regions: 48 files, 9 flagged, ~2,000 of ~40,000 rows actually checked by hand and 6 re-run locally to settle close calls."

**Browser and Drive data are context, not content.** They exist to name *what* was worked
on — a ticket key, a meeting, a console, a document — not to record browsing. The doc never
contains a URL, a visit count, a host list, an e-mail address, or anything from a page that is
not clearly work. If a page could be personal, it does not exist.

- ✅ "Reviewed the staging dashboards and the PROJ Kanban board; joined the team check-in."
- ✅ "Documents updated: Weekly Check-in (sheet)."
- ❌ "13 visits to eu-north-1.console.aws.amazon.com; 2 to acme.atlassian.net."

## Procedure

### 1. Locate the scripts

```bash
EOD="${CLAUDE_PLUGIN_ROOT:-$(find ~/.claude/plugins/cache ~/.claude/plugins/marketplaces -maxdepth 5 -path '*/eod-summary/*scripts/discover.py' 2>/dev/null | sort | head -1 | sed 's#/scripts/discover\.py$##')}"
ls "$EOD/scripts/"      # expect discover.py, distill.py, browser.py
```

If neither resolves, say so and stop — don't reimplement the scripts inline.

Use the session scratchpad for all intermediate files. Never write into the user's repos.

### 2. Discover the day

```bash
python3 "$EOD/scripts/discover.py" --date <DAY> --path <ROOT> > "$SCRATCH/discover.json"
```

Returns `{date, root, repos[], sessions[], stats}`. `repos` holds only repos active that day
(a commit, or a working-tree file whose mtime is that day). `sessions` holds that day's
transcripts with their `subagents[]` and each subagent's `description` label.

**If `repos` and `sessions` are both empty:** still run 2b and 2c if enabled. If those are empty too
(or disabled),
tell the user there was no activity and **do not create a doc**. Stop here.

### 2b. Browser layer — which sites were worked in

Only when `--browser` is set (or implied by `--browser-profile` / `--open-tabs`):

```bash
python3 "$EOD/scripts/browser.py" --date <DAY> [--profile <NAME>] [--open-tabs] > "$SCRATCH/browser.json"
```

Reads every Chrome profile's on-disk history for the local calendar day (no permission
needed; Chrome may be running). Returns hosts busiest-first with their page titles, extracted
Jira-style `issue_keys`, Google Meet `meetings`, and per-profile totals. Query strings and
e-mail addresses are already stripped; personal and auth hosts are excluded by default.

Read the file yourself — it is small — and note: which profile is the work one (each
profile's `account` shows only the e-mail domain, and every host is labelled with its
profile), ticket keys and `jira_projects`, meetings, consoles and dashboards, local preview
pages whose titles name the documents being built. **Ignore anything that is not obviously work.** If
`--open-tabs` was given and `open_tabs_error` mentions `-1743`, tell the user once how to grant
Automation permission and move on; history alone is enough.

### 2c. Drive layer — files updated in the working folder

Only when `--drive-folder NAME` is set — otherwise skip this layer entirely and don't mention
it. This layer runs through the Drive connector, not a script:

1. Load the schemas: `ToolSearch("select:mcp__claude_ai_Google_Drive__search_files,mcp__claude_ai_Google_Drive__get_file_metadata,mcp__claude_ai_Google_Drive__create_file")`.
2. Compute the day's UTC window from local midnight (the connector compares in UTC):
   ```bash
   python3 -c "import datetime as d,sys;s=d.datetime.fromisoformat(sys.argv[1]).astimezone();e=s+d.timedelta(days=1);f=lambda t:t.astimezone(d.timezone.utc).strftime('%Y-%m-%dT%H:%M:%SZ');print(f(s),f(e))" <DAY>
   ```
3. `search_files` for the folder: `title = '<drive-folder>' and mimeType = 'application/vnd.google-apps.folder'`.
   If several match, prefer the one that is shared with the team over personal copies; if
   none, say so in the chat report and skip the layer.
4. `search_files` for the day's changes anywhere in Drive (one call — Drive cannot query a
   folder *tree* directly):
   `modifiedTime >= '<start>' and modifiedTime < '<end>' and mimeType != 'application/vnd.google-apps.folder'`
5. For each hit, walk `parentId` upward with `get_file_metadata` (cache parents; stop at the
   target folder, a missing parent, or depth 6). Keep the files whose chain reaches the target
   folder. Record title and type; drop the rest — they are other people's or other projects'
   changes and are not this report's business.
6. Drive does not say *who* modified a file. Phrase these as "updated", never "you updated".

Result for the merge: a short list of `{title, type}` for the folder, or "nothing updated".

### 3. Distill each session

For every session, and every one of its subagents:

```bash
python3 "$EOD/scripts/distill.py" <transcript.jsonl> <DAY> > "$SCRATCH/<session8>_<label>.txt"
```

Expect roughly 400:1 — a 24 MB transcript lands around 14k tokens. Run these in one batched
command; they're independent and take milliseconds each.

Do **not** read the distilled files yourself — they exist to be handed to subagents in step 4.
Reading them all defeats the point.

### 4. One subagent per session

Spawn them **in parallel, in a single message** — one per session (not per subagent
transcript; a session's subagent digests go to that session's agent as extra input).

Each prompt must carry: the digest file paths, the session's project/cwd, the subagent
`description` labels, **the rules section verbatim**, and this required return shape:

```json
{
  "project": "<repo or folder name>",
  "headline": "<≤ 15 words, casual: what got done here>",
  "win": "<the single thing from this session most worth celebrating, ≤ 20 words, or null>",
  "achievements": ["<≤ 20 words each, outcome first, casual notebook voice — max 5>"],
  "decisions": ["<what was decided and why, one line — max 3>"],
  "loose_ends": ["<unfinished, blocked, or noted-for-later, one line — max 3>"]
}
```

Tell each agent explicitly: read the digest files, report the work done, write every item in
the casual notebook voice with the subject dropped (never "you did" or "Claude did"), omit anything about how the assistant went
about it, and skip trivia (file reads, retries, tool errors, counts of anything inspected
along the way). The caps are hard — if there is more, the agent picks the items that matter
tomorrow and drops the rest.

### 5. Merge

Combine the agents' JSON with the git layer from step 2, the browser context from 2b and the
Drive list from 2c into one report.

- **Deduplicate across layers.** A commit in `repos` and the session that produced it are one
  item, not two. The session usually has the better *why*; the commit has the better *what*.
- Group by project, not by session — several sessions on one repo become one section.
- **Pick the Wins** from the agents' `win` fields and the git layer — the 2–4 that matter
  most across all projects. A merge, a release, a root cause found or a plan settled beats a
  tidy-up. Leave them out of their project sections.
- Name a cross-project theme in the one-line "day in a sentence"; that's the part no single
  agent can see.
- **Browser context goes into existing bullets, or one extra bullet per project at most.**
  Use it to attach the ticket key to the work ("…on PROJ-547"), to name meetings attended, and
  to surface work that left no session or commit (a console reviewed, a board triaged). A
  ticket key seen in the browser and a branch of the same name are the same work item.
- **Drive files** become one bullet under the matching project — "Docs touched: A (doc),
  B (sheet)" — or a two-line `## Documents` section if they belong to no project. Cap at 6
  titles. Nothing updated → no bullet, no mention.
- Read diffs only where a commit message is too terse to summarize: `git show --stat` first,
  full `git show` only for small or ambiguous commits.

Target shape — the whole doc should look like this, and be about this long:

```markdown
# EOD notes — Tuesday, 22 September 2026

Big shipping day: the API auth refactor is finally in main, and the flaky-test mystery has an answer.

## Wins
- PROJ-142 merged to main (PR #31) — token handling behind one middleware, new session store, all tests green.
- Found why the checkout tests flake: a shared fixture leaks state between runs. Test code only, no product bug.
- Caching plan written up — what to cache, invalidation rules, no schema changes.

## api-service
- All review fixes in before the merge.
- Dependencies re-pinned; an unused SDK dropped.
- CLAUDE.md cut down to the real gotchas and now tracked; run/test details moved to the README.
- Code review turned up a few input-validation gaps — worth a ticket or two.
- PROJ board check + daily standup.

## web-app
- Settings page tidied: grouped sections, form errors shown inline.
- Pagination totals add up, but the "next" link skips a page on the last boundary. Oops.
- Slow dashboard load traced to one N+1 query, not the frontend bundle.
- New release-notes script reproduces last month's notes exactly.

## For tomorrow
- Fixture fix for the flaky checkout tests — write it and confirm 20 green runs.
- PROJ-150: nothing committed; the migration script and its tests are untracked.
- Before the caching work: measure current hit patterns, agree on TTLs.
- Still undecided: feature flag vs. separate endpoint for the new search.
```

The H1 is casual; the Drive **file title** stays `Work Summary — YYYY-MM-DD` (step 7 relies on it).

Before moving on, count the words. Over 500 means something is still narrating — cut it.

### 6. Privacy pass (required before publishing)

Session transcripts carry things git never saw. Before the doc is created, re-read the draft
and remove:

- anything credential-shaped — tokens, keys, connection strings, passwords, `.env` contents;
- absolute paths that expose unrelated private directories;
- client or customer specifics that aren't needed to state the outcome.

- anything that came from the browser layer and is not unambiguously work: personal
  documents, searches, shopping, social, health, finance. Also every URL and every visit count.

In the same pass, check the voice and length rules: Wins section present, casual notebook
voice (no report-speak), no "you" / "Claude", no session or transcript counts, no footer,
under 500 words.

This pass is not optional and applies even on `--dry-run` re-reads.

### 7. Publish

With `--dry-run`: print the summary in chat and stop.

Otherwise:

1. Load the Drive tool schemas first — MCP tools are deferred:
   `ToolSearch("select:mcp__claude_ai_Google_Drive__create_file,mcp__claude_ai_Google_Drive__search_files")`
2. `search_files` for a folder named **"Work Summaries"**; use it if found, otherwise create at
   root and tell the user to move it once.
3. `search_files` for the title `Work Summary — YYYY-MM-DD`. If it already exists (same-day
   re-run), create `Work Summary — YYYY-MM-DD (v2)` and say so. The connector has **no
   update/edit tool**, so appending to an existing doc is impossible.
4. `create_file` with the markdown.
5. Print the doc link in the final message.

### 8. Report

Close with a short block — not a restatement of the summary:

```
Work Summary — 2026-09-02
  Sources:  1 active repo (of 20 scanned), 2 sessions (6 transcripts distilled),
            Chrome: 2 profiles, 9 work hosts; Drive "Team Docs": 0 files updated
  Doc:      <link>
  Skipped:  3 sessions over the --max-sessions cap
```

Mention the cap only if it was hit, and flag when a session had no matching git activity —
that's the exploration-only case the session layer exists for, not an error. If the browser
layer showed a profile that looks personal, suggest `--browser-profile` once. This block is
the **only** place source statistics appear; never copy them into the doc.

## Known limitation

A single running/appended doc is impossible via the Drive connector; it creates one doc per
day. Appending would need a Google Apps Script web-app endpoint to POST to — not implemented.
